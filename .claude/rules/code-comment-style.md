# コードコメントスタイル規約

中心思想は次の 2 点。

1. **役割の境界を書く** — その crate・module・型が、認証基盤全体のどの境界を担い、何に依存しないかを書く
2. **読み手は渡された情報からしか判断できない** — 後続の読み手（人・AI）は spec や他 crate を辿れるとは限らない。
    離れた場所の前提・契約・根拠（spec ID）をコメントで「その場」に持ち込む

コメントの言語は日本語を基本とする（`./japanese-style.md`）。コードの書き方そのものは `./coding-rust.md`、
秘密値の扱いは `./secret-values.md` が担当する。

## `//!`（crate・module）

各 crate の `lib.rs` / `main.rs` と、責務を持つ module の先頭に書く。

- その crate・module の役割と責務の境界（何を担い、何を担わないか）
- 依存の向き: 依存してよいもの・してはならないもの（例: `core` は非同期ランタイム・DB ドライバ・HTTP サーバーに
  依存せず、時刻・乱数・ID を引数で受ける — DPOL-1・DPOL-3）
- 誰から呼ばれるか（`server` から、RP から、migrate bin と試験ビルドだけから等）

```rust
//! 認証コア。I/O を持たないドメインの判定だけを担う。
//!
//! 時刻・乱数・ID は呼び出し元から引数で受け、ここでは読まない（DPOL-1・DPOL-3）。
//! 非同期ランタイム・DB ドライバ・HTTP サーバー・web-sys に依存しない（DPOL-1）。
```

## `///`（公開 API）

公開する型・関数・trait・トレイトメソッドに書く。シグネチャの言い換えは書かない。

- 契約: 何を保証して返すか、呼び出し元が前提とする状態
- `# Errors`: 返しうる誤りとその意味（外に出す失敗理由を 1 種類に畳む等の扱いは呼び出し元に伝える — THRT-25）
- `# Panics`: panic しうる条件。panic しない設計なら書かない
- 時刻・期限の比較の向き（例: `exp == now` は拒否 — SIGN-17）など、取り違えると安全性が崩れる前提

```rust
/// 秘密値を明示的に取り出す唯一の経路（SECR-16。検討中）。
///
/// ハッシュ化・署名・外部への送信の箇所でだけ呼ぶ。戻り値をログ・誤り応答に渡さないこと。
pub fn expose(&self) -> &str { /* ... */ }
```

## インラインコメント（`//`）

- why（なぜその実装か）を書く。what はコードが示す
- 根拠は spec ID・決定 ID で書く。本文を写さない（`./spec-reference.md`）

```rust
// SECR-11: Debug は値・長さ・ハッシュを含まない固定文字列にする
// AUDB-35: 認証経路では読んでから書く形を使わず、1 文の条件付き更新にする
// CSRF-7: Gate の登録箇所はここ 1 つ。外す分岐を足さない
```

- 未決の値は「未定（TASK-n で決める）」・仮定 ID（`A-2026-10-28-n`）を添え、仮の値であることを明示する
- `TODO` には追跡先（`TASK-N` か Issue 番号）を付ける（`./out-of-scope-tracking.md`）

## 書かないもの

- 秘密値・トークン・鍵・パスワード・復旧コードの実例、JWT 形の文字列（例示も含む。`./secret-values.md`）
- 実機の名前・ホームのパス・内部のアドレス
- 他所有者（Hub・fandhe-backend・fandhe-frontend・fandhe-db）の値や本文の写し。ID で引く
- シグネチャを読めば分かる逐語的な説明、解決済みの経緯だけを残したコメント
- spec のステータスに反する断定（「検討中」の項目を「確定」と書かない。ACPT-7）

## `unsafe` と `# Safety`

各 crate は `#![forbid(unsafe_code)]` を既定とする（利用者決定 2026-11-13）。そのため `# Safety` 節と
`// SAFETY:` コメントは原則不要。例外として利用者が承認した `unsafe` には、承認の記録（日付・理由・範囲）と
`// SAFETY:` で守る不変条件を書く。

## シェルスクリプト（`scripts/**`）

- 先頭に役割と呼び出し元（Makefile のターゲット・`lefthook.yml`・CI のジョブ）を日本語で書く
- 終了コードの意味・fail-closed にしている理由など、取り違えると検査が素通りする前提を書く
- 書き方の規約は `./makefile.md`、`scripts/hooks/**` は `./git-hooks.md` を参照する

## 注意事項

- コメントは実装の変更と同じ変更で更新する。乖離したコメントは無いより有害
- 認証・権限・秘密値・CSRF・Cookie の前提は特に丁寧に書く（`./security.md`）
