# フィッシングの受容性の観察の手順

`TASK-127` の 3/4（#3927）。承認の画面で、攻撃者の役が始めた要求と本人の役が始めた要求を、送信元の違いから見分けて拒否できるかを人が観察し、画面の手掛かりの材料にする手順である。
共通の原則は [README.md](README.md)。根拠は `D-2026-10-17-51` の (1) と `ACPT-7`。観察の実施は `TASK-130`（Hub へ移管済み）。正は spec repo の `04-behavior/`。

## 準備（人）

1. `TASK-126` の基準（観察の人数・拒否できた割合）が決まって記録されているかを確かめる。決まっていなければ止める（値は未定）。
2. 評価する画面と版（commit）を控える。`UISF-37` の操作にあるとおり、手掛かりを足した版と足さない版の 2 つを用意する。
3. 役割を決める。進行役、観察者、攻撃者の役の要求を始める操作者で、いずれも人である。
4. 参加者を集める。人数は基準に従う。参加者は番号で引き、個人情報は記録に書かない。
5. 環境は検証用のものを使う。検証用の本人・passkey・クライアントを使い、ユーザーコードも検証用の値にする。承認しても検証環境の外に効かない構成にする。攻撃者の役は検証環境の中の人の操作者に限り、実在の第三者に対してフィッシングを行わない。
6. 攻撃者の役と本人の役が、別の送信元から要求を始められるように用意する。アドレス・ホスト名・ネットワークの名前は手順書にも記録にも書かず、「本人の役の送信元」「攻撃者の役の送信元」のラベルで引く。
7. 攻撃者の役の申告した環境は、本人の役の申告と同じ文字列にそろえる（PoC-9 の手順 6 の実プロセスの試験の構成に合わせる）。
8. 録画・録音は既定では取らない。コードが映り込むためで、取るかどうかは人が決める。

## 観察の手順

参加者ごと、版ごとに同じ順で行う。

1. 参加者に本人の役を担ってもらう。本人の役の要求をエージェントの側の表示から始め、別の送信元から攻撃者の役が始めた要求のユーザーコードを参加者に渡す。渡し方・提示する順・回数・2 つの版の順は人が決める（書き手の観点。spec に定めが無い）。
2. 参加者が各ユーザーコードを自分で入力し、承認の画面で承認か拒否かを選ぶ。進行役・観察者は口を挟まない。
3. 観察者は次を記録する。
    - 攻撃者の役の要求を拒否できたか。
    - 本人の役の要求を承認したか。
    - 「開始の送信元」の欄の違いに気づいたか。開始の時刻やユーザーコードの照合の案内を手掛かりにしたか。
4. 課題の後に短い聞き取りをする（何を見て判断したか）。
5. 手掛かりを足した版と足さない版で、同じ流れを繰り返して比べる（`UISF-37` の操作）。2 つの版の差は手掛かりの有無に限り、ユーザーコードを URL に含める案内など検証を緩める変更を入れない（`UISF-13`）。
6. 事前にどこまで説明するか（フィッシングの観察だと伝えるか）は人が決める（書き手の観点。spec に定めが無い）。伝えない場合は、観察の後に種明かしと説明を行う。
7. ユーザーコード・送信元の実際の値は記録に写さない。

記録の項目と照合欄の様式は 4/4（#3928）で作る。ここでは、何をどの順で観察するかまでを定める。

## 人が行う旨

- 観察・拒否できたかの判断・記入・判定・手掛かりを足す判断は人が行い、AI・自動処理（LLM の要約による判定を含む）に代えない（`D-2026-10-17-51` の (1)、`ACPT-7`）。承認の操作も本人の役の人が画面で行い、AI・自動処理に承認させない（`DVUI-10`）。
- PoC-9 の自動の試験（WebDriver による操作の模擬）の結果は、受容性の結果として扱わない。
- AI が書いてよいのは手順書と空の様式までである。評価の結果で行のステータスを確定に変えるのは、人の記録による（`ACPT-7`）。
