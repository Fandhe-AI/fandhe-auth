# 支援技術とキーボード操作の確認の手順

`TASK-127` の 2/4（#3926）。スクリーンリーダーとキーボードだけの操作で、各画面の操作を最後まで完了できるかを人が確かめ、対応の修正の材料にする手順である。
共通の原則は [README.md](README.md)。根拠は `D-2026-10-17-51` の (1) と `ACPT-7`。確認の実施は `TASK-129`（Hub へ移管済み）。正は spec repo の `04-behavior/`。

## 準備（人）

1. `TASK-126` の基準（対象とする支援技術の種類・合格の割合）が決まって記録されているかを確かめる。決まっていなければ止める（値は未定）。
2. 評価に使う支援技術の組み合わせを、利用者が指名した人が決めて控える（`TASK-129`）。この手順書には製品名・版・OS とブラウザの組み合わせを書かない。
3. 評価する画面と版（commit）を控える。
4. 確認者を決める（人）。確認者は番号で引き、個人情報は記録に書かない。
5. 環境は検証用のものを使う。passkey は検証用の authenticator と検証用の本人で用意する。ユーザーコード・復旧コード・確認コードも検証用の値にする。
6. 録音・画面の録画は、コードや秘密値が映り込むため既定では取らない。取るかどうかは人が決める。取る場合も、値が入る部分は記録に残さない。

## 確認の順序

支援技術の組み合わせごとに、次の順で 1 巡する。

1. 画面群 A、B、C の順に進める。
2. 各画面群の中では、先にキーボードだけの操作の確認を行い、次にスクリーンリーダーを起動した状態で同じ操作を行う。
3. 画面群ごとの操作の例は次のとおり。
    - A: ログイン、再認証、passkey の追加・削除、認証セッションの一覧と失効。
    - B: 招待の発行と受け入れ、復旧、管理者の操作。
    - C: ユーザーコードの入力、承認・拒否、一覧からの失効。

## キーボードだけの操作の確認

- マウス・タッチは使わない。各操作を最後まで完了できたかを、操作ごとに記録する。
- 次は書き手の挙げた観察の観点であり、合否の基準ではない（spec に定めが無い）。
  - フォーカスが見えるか。
  - 移動の順が操作の順と合っているか。
  - フォーカスが抜け出せなくならないか。
  - 誤りを表示した後にフォーカスがどこへ行くか。
- OS やブラウザが出す passkey のダイアログは画面の外にある。画面の中の操作とは分けて記録し、扱いは人が決める。

## スクリーンリーダーでの確認

- 画面群 C は `DVUI-27`（→ Hub `ASCR-72`）の観点で確かめる。
  - 承認対象の各項目のラベルと値が対応付けて読み上げられるか（項目は `UISF-24`）。
  - 承認・拒否・失効の操作が名前で識別できるか。
  - 読み上げを頼りに操作を完了できるか。
- 画面群 A・B も、同じ操作を読み上げを頼りに完了できるかを見る（`LGUI-39`（→ Hub `ASCR-69`）、`IRUI-30`（→ Hub `ASCR-77`））。
- コードの値が読み上げられても、その値を記録に写さない。

記録の項目と照合欄の様式は 4/4（#3928）で作る。ここでは、何をどの順で確認するかまでを定める。

## 人が行う旨

スクリーンリーダーの読み上げの確認・キーボード操作の確認・記入・合否の判定・修正の判断は人が行い、AI・自動処理に代えない（`D-2026-10-17-51` の (1)、`ACPT-7`）。
自動のアクセシビリティ検査の道具の出力と AI の出力は、評価の結果として扱わず、参考の材料に留める。
AI が書いてよいのは手順書と空の様式までである。評価の結果で行のステータスを確定に変えるのは、人の記録による（`ACPT-7`）。
