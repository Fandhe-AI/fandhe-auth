# 検討中から確定への変更の手順

`TASK-74`（検討中から確定への変更の手順と集計の道具）の手順書。根拠は `ACPT-7`（`docs/spec/04-behavior/acceptance-retest.md`。操作 (1)〜(4)・期待）である。
本文は写さず、ID で引く。ステータスの正（SSOT）は spec repo の `04-behavior/` で、この repo の `docs/spec` は直接編集しない（`.claude/rules/spec-reference.md`）。

この文書は手順の説明であり、確定への変更そのものではない。判定は人が行う。

## 原則

- 道具は「人の判定が要る変更」を漏れなく検出して止めるだけで、変更が正しいかは判定しない。正しさは人が判定票で判定する。検出の範囲は広く取り、判別できなければ止める（fail-closed）。
- AI・自動処理は「確定」にしない。確定への変更の判定は人が記録する（`ACPT-7` の期待の 3 文目）。試験の実行と記録の収集は自動でよい。
- 段 3 の対象の commit を AI・自動処理が作らない。trailer を外して検査を通すのは迂回に当たる。PR なしの push は失敗とし、merge の実行者も人とする。
- ラベルの禁止（この節が正本。他の文書は参照する）:
  - 〔仮想〕の合格で〔実機〕〔人の操作〕の項目を確定にしない（`ACPT-7` の期待の 1 文目）。
  - 〔モック〕〔資料〕の合格を〔実機〕〔人の操作〕の確定に使わない（禁止）。根拠は `docs/spec/02-poc-plan.md` の「Go/No-Go 判断基準」節（〔モック〕〔仮想〕〔資料〕の合格を〔実機〕〔人の操作〕の合格に読み替えない）と `.claude/rules/verification.md`（〔仮想〕〔モック〕の合格で〔実機〕〔人の操作〕を確定扱いしない）。`ACPT-7` の期待の 1 文目が名指すのは〔仮想〕だけだが、禁止の範囲はそれに限らない。
  - 次の 2 点は書き手の読み（厳しい側）である。`ACPT-8` の「仮想 authenticator の合格は、実機の合格として数えない」は、〔実機〕と〔人の操作〕の両方に掛かると読む（`docs/spec/02-poc-plan.md` の「記録の形」節も参照）。自動の〔実機〕の実行は、authenticator を使う項目では仮想 authenticator に当たると読む（02 の「検証の種類のラベル」節）。この読みにより、authenticator を使う項目は〔人の操作〕だけを認め、DB・プロセスの〔実機〕の項目は〔実機〕を認める。
- 期待が成り立たないときは期待を緩めず、逆戻りの提案として報告する（`ACPT-7` の操作 (4)）。
- 仕様の変更は `04-behavior/` から始め（段 3。ステータスサマリーは `04-behavior/README.md` の中にあり、同じ差分に入れる）、`05-tasks.md` と `spec.md`（自動生成。再生成する）は後で追随させる（段 4。SSOT）。
- 道具が 0 件を返しても、それは判定ではなく材料である（`.claude/rules/verification.md`。ゲートの通過は spec の「確定」ではない）。
- 秘密値・実機の名前・ホームのパス・内部のアドレスを書かない（`.claude/rules/security.md`）。

## 段 3 の対象

段 3 の対象は、spec repo の 1 つの PR の差分のうち、次のどれかを含むものである。

1. 確定の行（変更の前か後）の行全体（ID・優先度・ステータス・本文の全ての文字）の変更、行の追加・削除・移管・置き換え。確定の行の根拠欄に `**試験の記録**` を足すことも含む（判定は「範囲を変えない」と人が確かめる形でよい）。
2. ファイル冒頭・行頭の「確定の範囲」の宣言の変更。
3. 確定の行の移管と、欠番の ID の復活（移管表の変更のうち）。
4. ステータスサマリー（spec repo の `04-behavior/README.md`）の変更のうち、確定の件数が変わるとき、または段 5 の集計と一致しないとき。
5. 確定の定義と読み方を決める文書の変更: `04-behavior/README.md` の ID 規約・`CG2-4` の段落、各ファイルの適用範囲と冒頭の注記、`02-poc-plan.md` のラベル・記録の形・Go/No-Go 判断基準の節、`ACPT-7`〜`ACPT-11` の行（対応 ID の欄を含む）。
6. どの行でも `**確定の記録**` の追加・変更。検討中の行の `**試験の記録**` への結果・件数・記入者・判定者の記入は、通常の段 1 の作業で段 3 の対象ではない（人が書き、自動・AI は書かない。確定の行に触れる場合は対象 1、確定の記録の場合は本項の対象）。
7. 確定の行が引く先の変更: 確定の行が ID で引く行（例: 期待を他の ID に委ねる場合）、`01-brainstorm.md` の `A-`・`D-`、`03-poc/**` の全ファイル。引く先の一覧と突き合わせられるまでは要確認として止め（fail-closed）、人が段 3(c) で確かめる。参照先だけを変えると、確定の行の文字列は変わらない。参照元の前提・操作・期待や範囲が実質的に変わるときは、参照元の (ID, 範囲) ごとに新しい根拠で再判定する（R4・R6 の再判定。種類は U-13）か、確定から検討中に戻す。新しい `D-`・`A-` の追加は、同じ差分で確定の行から引かれない場合に限り対象外である。同じ差分で確定の行から引かれる新しい ID は、参照元の行（対象 1）とあわせて本対象に入れ、R2 の照合に含める（変更の前後の参照を比べて確かめる）。

検討中の行への `**試験の記録**` の追記・結果の記入だけの差分は、対象外である（上の 1 の追記は、確定の行に限る）。
確定の行の期待の変更は、段 3 を経ない限り失敗である。検討中の行の期待を緩める変更は、後で確定にするときの判定材料として人に示す。
道具の未提供の間も同じで、手で確かめる。

## 段 3(c) の確かめる項目

人が確定の前に確かめ、判定の記録に残す。

- 判定者が実際に人であること（道具は判定できない）
- 検証の種類（ラベル）と範囲が、項目の要求に合うこと（U-4 の暫定の集合の外の項目を含む）
- `ACPT-7` の前提の解消（再試験・決定・受け入れ試験が済み、検討中の理由が解けたこと。判定表に D-・TASK- の参照を残す）
- 範囲を分けた場合、分けた残りの検討中の行が同じ差分にあり、互いに ID で引いていること（[scope-rule.md](scope-rule.md)）
- 対象の版が今回の版と一致すること、`spec.md` を比べる基準（比べ方は `tools.md`〔後続の PR〕で定めるまで人が確かめる）
- 確定の行に `**試験の記録**` を足す差分では、範囲を変えないこと
- 実施者が手順を行う担当（利用者）であること（`D-2026-10-27-5`）
- 確定の行が引く先の変更（段 3 の対象の 7。道具は突き合わせられないものを要確認として止める。中身の判定は人）
- サマリーの件数が表の集計と一致すること、`05-tasks.md`・`spec.md` が `04-behavior/` より先にステータスを変えていないこと（人が手で数えて確かめる）
- `document-quality.md` の SSOT の原則と `migration/library-boundary-map.md` の変更（段 3 の対象 5 に入れるかは U-12 で利用者の判定待ち。入れるまでは人が確かめる）
- 段 6 の逆戻りの提案が、期待が成り立たないと確かめた時点で報告されていること。確定の行に不合格の記録があるときは、その提案が作られていること（道具では検査しない）
- R1〜R7 の各条件を全て人が手で確かめる（道具の有無によらない）。少なくとも次を並べる。
  - (i) 差分の段 3 の対象と判定票の行が両方向で一致する
  - (ii) 判定の値が種類ごとの肯定の値である
  - (iii) 判定票の base・head が今回の PR と一致する
  - (iv) R4 の全条件（対象の版が今回の版と一致すること、判定票の (ID, 範囲, ラベル, 版, 結果) と記録が一致すること、結果が合格・n=m・〔人の操作〕の 4 欄・〔仮想〕の範囲の語・環境が予定・`-` でない・ラベル・判定者・記入者）

## 道具

`scripts/spec-status-count.sh`（集計と README の表との突き合わせ）と `scripts/spec-status-check.sh`（全行の検査と変更の検査）は、後続の PR で追加する。
使い方・終了コード・検出の区分は `tools.md` に書く（同じく後続の PR）。この PR の時点では、どちらも存在しない。

### 道具の限界

- 道具は spec を読むだけで、書き込まない。検出の件数が 0 でも、確定への変更が人の判定であったことの証明にはならない。
- 誰が記入したかは証明できない。spec repo の commit の作者・trailer では人と AI を区別できず（AI が手伝った commit が多数ある）、判定者・記入者の欄は人の自己申告である。
- 件数 0 は代理の指標である。最終の確かめは人が行う（`ACPT-7` の期待の 3 文目。`.claude/rules/verification.md`）。
- 規則と道具の変更は人のレビューを経る。陽性の fixture を減らさない。
- spec repo の CI では流さないので（U-10）、道具が止めるのは材料であり、強制ではない。
- 道具は、突き合わせられない引く先の変更を要確認として止める（0 件は通過を意味しない）。中身の判定は人が段 3(c) で行う。
- spec repo は private で、実データの検査はローカルに限る。権限のない環境（CI・外部の貢献者）では、検査不能として扱う（`.claude/rules/spec-reference.md`）。

## U-9 の要件（暫定。利用者の判定待ち）

PR 1 の手順は、道具が無くても人だけで回ることを正とする。道具への要件は次の R1〜R7 だけを残す。
それぞれの細目（版の比べ方・単位の書き方・参照の手段）は `tools.md`（後続の PR）で fixture とともに定める。決まるまでは段 3(c) で人が確かめる。

- **R1**: 道具は検出して止めるだけで、変更の正しさは判定しない。判別できなければ止める（fail-closed）。要確認・検査不能・解釈できない行は、0 でない終了コードで止め、人が解くまで進めない。
- **R2**: 差分と判定票は両方向で一致する。差分の段 3 の対象の全てに判定票の行があり、判定票の全ての行が差分にある。
- **R3**: 判定の値は、種類ごとの肯定の値だけを通す。「確定にする」「範囲を広げる」「行の追加（確定で足す）」→「確定にする」、「範囲を変えない追記」→「範囲を変えないことを確認」、「確定から検討中に戻す」→「戻す」、その他→「確認済み」。否定・保留・空・「指摘あり」は止める。
- **R4**: 確定の記録は差分の側から引く。差分で確定になる・範囲が広がる全ての (ID, 範囲) と、確定のまま前提・操作・期待を変える全ての (ID, 範囲)（R6 の再判定）に、今回の差分で追加された、今回の版の合格の `**確定の記録**` があり、判定票の行の (ID, 範囲, ラベル, 対象の版, 結果) と一致する。判定票の「根拠欄の記録の参照」（日付・環境・commit と記録の位置を含む。[judgment-form.md](judgment-form.md)）は 1 件の記録に一意に解決でき、その記録自体が今回の差分で足されたもので、以下の条件を満たすこと（base にある旧記録を指す参照は通さない）。合格の `**確定の記録**` の条件は次の全てである。
  - 対象の版が今回の版と一致する（旧版の記録で代替しない。`scope-rule.md`）
  - 今回の差分（spec の base から head）で追加された記録である（base に既にある記録は、同じ対象の版でも代替にしない。(ID, 範囲) ごとに照合する）
  - 結果が `合格`
  - 件数が `n/m` で n=m の数値で、対象の数が正（m≥1。`0/0` を通さない）である（`-` を含まない）
  - 必須欄がある（〔人の操作〕の確定の記録では `手順=`・`機材の種類=`・`ブラウザの版=`・`実施者=` を含む。〔人の操作〕は (ブラウザ, authenticator) の組ごとに 1 件で、確定の範囲は記録のある組だけ）
  - ラベルが (ID, 範囲) の要するラベルと一致する（下の注）
  - ラベルが〔仮想〕なら、環境に範囲の語（「仮想 authenticator の範囲」。ID 規約 (a)）がある
  - 環境が `環境=予定:…`・`環境=-` でない
  - 判定者・記入者の欄が空でなく、AI・自動処理を示す値でない（代理の検査。人かどうかは道具では判定できず、人が段 3(c) で確かめる）
  - 合格の記録があっても、差分で新しく足した・変えた全ての `**確定の記録**` を検査し、合格以外（結果が `合格` でない・n<m・`-` を含む等）が 1 件でもあれば止める（合格の記録で相殺しない）
- **R5**: 判定票は PR に結び付く。判定票に spec の base と head の commit の欄があり、検査する差分と一致する。head は判定票を保存する前の対象の PR のブランチの先頭で、判定票を対象の PR のブランチにコミットしない（コミットすると head が変わり一致しなくなる）。判定票は対象の PR のブランチとは別の参照（別ブランチ・別 PR など）に置き、保存しても検査の対象の head が変わらないようにする。置き場の path と参照の形は U-8 と同じく未定（利用者の判定待ち）。
- **R6**: 機械で分かる変化（検討中から確定・確定から検討中・行の削除・確定での行の追加）は道具が種類を決め、判定票と食い違えば止める。spec 内の移管先が確定の行として現れる場合は「移管・削除」の例外を優先する。条件は、移管元が差分の前に確定で、同じ差分で消えて移管表に載り、移管先が確定の内容（前提・操作・期待）と範囲を変えずに維持することである。検討中の行を移管先で確定にする・移管先で期待や範囲を変える・再検証が要る変更は例外にせず、R4 を適用する。それ以外の確定での行の追加は、変更の種類を「行の追加」（確定で足す場合）とし、判定の値は「確定にする」を要する（R3。今回の版の合格の確定の記録が要る）。確定の行の前提・操作・期待の変更は「確定にする」（今回の版の合格の確定の記録が要る）か「確定から検討中に戻す」に限り、「文面の変更」では通さない。誤字のような変更の扱いは利用者の判定待ち。例外として、前提・期待の変更が範囲を狭めるだけ、または移管だけなら、「範囲を狭める（分割）」「移管・削除」の種類で「確認済み」として通す。条件は、分けた残りの行・移管先が同じ差分にあること。この例外は、条件を全て満たす間、R4 の「今回の差分で追加された記録」の要求に優先する（既存の確定の記録を維持し、狭めた後の範囲が既存の記録の環境に含まれ、期待・環境・範囲を広げず変えない場合）。範囲を広げる・環境を足す・期待を変える変更は例外にならず、R4 を適用する。分割で残す既存の確定の記録の環境は、狭めた後の範囲より広くてよい。道具は、残した記録が狭めた後の範囲を含むことを確かめ、確定の範囲は行頭の狭い範囲に限る（[scope-rule.md](scope-rule.md)）。どちらか判別できなければ止める（R1）。
- **R7**: ラベルの割り当てが未定で止めるのは「確定にする」「範囲を広げる」と確定での行の追加だけである。逆戻り・移管・追記は止めない。

**変更の種類**: 「確定にする」「範囲を広げる」「範囲を狭める（分割）」「範囲を変えない追記」「確定から検討中に戻す」「行の追加」「移管・削除」「文面の変更」「規則の文書の変更」（[judgment-form.md](judgment-form.md)）。

**違反の例**（R1〜R7 の例示で、網羅ではない）: (i) 段 3 の対象を含む PR に判定票が無い、または参照されない／(ii) 判定票の行が差分と一致しない／(iii) 判定の値が肯定の値でない／(iv)「確定にする」「範囲を広げる」の対象に対応する `**確定の記録**` が無い／(v) 記録の対象の版が今回の版と一致しない／(vi) 結果が `合格` 以外・件数が n<m または `-` を含む／(vii) 必須欄の欠け・環境が `環境=予定:…`・`環境=-`・ラベルの不一致・判定者・記入者が空、または AI・自動処理を示す値。

**注（ラベル）**: authenticator を使う (ID, 範囲) は〔人の操作〕だけを認める（自動の〔実機〕の実行は仮想 authenticator に当たると読み、通らない）。DB・プロセスは〔実機〕を認める。〔仮想〕〔モック〕〔資料〕はどちらも通らない。要するラベルは U-4（暫定）である。ラベルは自己申告で、通っても〔人の操作〕だったことの証明にはならない（段 3(c) で人が確かめる）。

**全行の不変条件（段 5）**: 全ての確定の行にラベル付きの根拠がある（数え方は U-11。結果は材料）。〔仮想〕の確定に範囲の語がある（ID 規約 (a)）。サマリーの確定・検討中・合計が表の行の集計と一致する（不一致は失敗）。
