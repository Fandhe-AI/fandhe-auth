# 検討中から確定への変更の手順

`TASK-74`（検討中から確定への変更の手順と集計の道具）の手順書。根拠は `ACPT-7`（`docs/spec/04-behavior/acceptance-retest.md`。操作 (1)〜(4)・期待）である。
本文は写さず、ID で引く。ステータスの正（SSOT）は spec repo の `04-behavior/` で、この repo の `docs/spec` は直接編集しない（`.claude/rules/spec-reference.md`）。

この文書は手順の説明であり、確定への変更そのものではない。判定は人が行う。

## 原則

- AI・自動処理は「確定」にしない。確定への変更の判定は人が記録する（`ACPT-7` の期待の 3 文目）。試験の実行と記録の収集は自動でよい。
- 確定への変更の commit を AI・自動処理が作らない。trailer を外して検査を通すのは迂回に当たる。
- 〔仮想〕の合格で〔実機〕〔人の操作〕の項目を確定にしない（`ACPT-7` の期待の 1 文目。仮想 authenticator と実機の関係は `ACPT-8` で、〔実機〕の側だけに掛かる。〔人の操作〕の根拠は `docs/spec/02-poc-plan.md` の「Go/No-Go 判断基準」節と `.claude/rules/verification.md`）。〔モック〕〔資料〕の合格を〔実機〕〔人の操作〕の確定に使わない（禁止）。根拠は `02-poc-plan.md` の「Go/No-Go 判断基準」節（〔モック〕〔仮想〕〔資料〕の合格を〔実機〕〔人の操作〕の合格に読み替えない）と、`.claude/rules/verification.md`（〔仮想〕〔モック〕の合格で〔実機〕〔人の操作〕を確定扱いしない）。`ACPT-7` の期待の 1 文目が名指すのは〔仮想〕だけだが、禁止の範囲はそれに限らない。
- 期待が成り立たないときは期待を緩めず、逆戻りの提案として報告する（`ACPT-7` の操作 (4)）。
- 仕様の変更は `04-behavior/` から始め（段 3）、サマリー・`05-tasks.md`・`spec.md` は後で追随させる（段 4。SSOT）。
- 道具が 0 件を返しても、それは判定ではなく材料である（`.claude/rules/verification.md`。ゲートの通過は spec の「確定」ではない）。
- 秘密値・実機の名前・ホームのパス・内部のアドレスを書かない（`.claude/rules/security.md`）。

## 道具

`scripts/spec-status-count.sh`（集計と README の表との突き合わせ）と `scripts/spec-status-check.sh`（全行の検査と変更の検査）は、後続の PR で追加する。
使い方・終了コード・検出の区分は `tools.md` に書く（同じく後続の PR）。この PR の時点では、どちらも存在しない。

### 道具の限界

- 道具は spec を読むだけで、書き込まない。検出の件数が 0 でも、確定への変更が人の判定であったことの証明にはならない。
- 誰が記入したかは証明できない。spec repo の commit の作者・trailer では人と AI を区別できず（AI が手伝った commit が多数ある）、判定者の欄は人の自己申告である。
- 件数 0 は代理の指標である。最終の確かめは人が行う（`ACPT-7` の期待の 3 文目。`.claude/rules/verification.md`）。
- spec repo は private で、実データの検査はローカルに限る。権限のない環境（CI・外部の貢献者）では、検査不能として扱う（`.claude/rules/spec-reference.md`）。
